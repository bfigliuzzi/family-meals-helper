# Family Meals Helper

App desktop (Tauri + React + TypeScript) qui compose des menus de batch cook avec Claude, puis produit la liste de courses et une fiche PDF. Toute la logique métier vit dans `packages/core`, sans dépendance à Tauri, pour pouvoir passer plus tard sur un serveur web.

- **Comportement du produit, règles, architecture** → `docs/superpowers/specs/2026-11-12-family-meals-helper-design.md`. Source de vérité : en cas de doute sur ce que l'outil doit faire, elle tranche.
- **Lot en cours, ordre des lots, livrable attendu** → `docs/roadmap.md`. Un lot livré y passe au statut `livré`.
- **Valeurs des règles** (durées de conservation, seuils d'équilibre, sources de prix) → `docs/research/`, un fichier par source ; chaque fichier dit en tête comment le lire.
- **Écrire du code dans `packages/core`** (où va le code Node, globales permises, accès extérieurs par les ports, règle pour ajouter une règle ESLint) → `docs/conventions-core.md`. À lire avant de toucher à `core`.

## Commandes

Versions figées : Node 24.22.3 (`.node-version`, à activer avec `fnm use`), pnpm 12.18.0 (champ `packageManager`, pnpm le télécharge seul), Rust 1.100.0 (`rust-toolchain.toml`, via rustup).

- Tout vérifier : `pnpm install --frozen-lockfile && pnpm lint && pnpm format:check && pnpm typecheck && pnpm test && pnpm build`. C'est ce que lance le job `check` de la CI (Ubuntu). Un second job, `rust` (macOS), lance les trois commandes Rust ci-dessous.
- Lancer l'app : `pnpm --filter desktop tauri dev` (port 1420, premier lancement long : compilation Rust). Après l'arrêt, vérifier que le port est libre (`lsof -nP -iTCP:1420 -sTCP:LISTEN`) et que l'app ne tourne plus : pnpm 12 laisse parfois Vite ou l'app en vie.
- Tester l'app : `pnpm --filter desktop test` (Vitest et jsdom ; `pnpm test` les lance aussi). Tests Rust, depuis la racine : `cargo test --locked --manifest-path apps/desktop/src-tauri/Cargo.toml`. Les deux autres commandes du job `rust`, depuis la racine : `cargo fmt --check --manifest-path apps/desktop/src-tauri/Cargo.toml` et `cargo clippy --locked --all-targets --manifest-path apps/desktop/src-tauri/Cargo.toml -- -D warnings` (le job les lance sans `--manifest-path`, depuis `apps/desktop/src-tauri`). `cargo` vient de rustup : si le shell ne le trouve pas, `export PATH="$HOME/.cargo/bin:$PATH"`.
- Données de l'app (macOS) : la base des réglages est `~/Library/Application Support/com.familymealshelper.desktop/family-meals-helper.db` (avec `family-meals-helper.lock`, le verrou qui laisse une seule instance accéder aux réglages). La clé d'API est dans le trousseau, service `com.familymealshelper.desktop`, compte `anthropic-api-key`. Pour voir si elle existe sans l'afficher : `security find-generic-password -s com.familymealshelper.desktop -a anthropic-api-key; echo "code $?"` (jamais `-w` ni `-g`). L'app lit la clé dans le trousseau ; la ligne de commande garde `ANTHROPIC_API_KEY`. La base est en `user_version` 2 depuis le lot 6.5a : la table `history` garde les 5 derniers menus validés, avec la fiche PDF en BLOB dans la ligne (ajout et purge dans une seule transaction). Le dossier `history/` à côté de la base ne contient que des copies `<id>.pdf`, réécrites à chaque ouverture dans Aperçu (celles des entrées purgées sont supprimées à l'ouverture suivante) : la source de la fiche est la base. Une app du lot 6.4 ou antérieure refuse une base en version 2 (« Base créée par une version plus récente de l'app. »).
- Écrire du Rust dans l'app : pour ajouter une commande, la déclarer dans `apps/desktop/src-tauri/build.rs` (`AppManifest::commands`), dans `capabilities/default.json` et dans `generate_handler!` de `src/main.rs` ; les fichiers `permissions/autogenerated/*.toml` sont committés. Les paquets `@tauri-apps/api` et `@tauri-apps/cli` gardent la même version mineure que la crate `tauri` (2.12 : la CLI Tauri refuse un écart) ; `tauri-build` et `tauri-utils` ont leur propre numérotation. La vue web ne récupère jamais la clé stockée (`secret_status` ne rend qu'un booléen). La clé ne sort du Rust que par `ai_send` (`src/ai_transport.rs`) : la commande la lit dans le trousseau à chaque appel, l'envoie seulement à `https://api.mammouth.ai/v1/messages`, un appel à la fois, et ne la laisse jamais revenir à la vue web. La clé ne contient que des lettres sans accent, des chiffres, `-` et `_` (`checkApiKey` et `check_secret`) : aucun échappement JSON ou JavaScript ne la touche, sa forme littérale est sa seule écriture dans un texte JSON. Le Rust ne transforme jamais le corps de la réponse : il le rend octet pour octet, ou pas du tout (`check_body`). Un corps est rendu s'il est du JSON que `serde_json` lit et que la clé n'est ni dans le texte reçu (ce qui couvre un nombre) ni dans une chaîne ou un nom de champ décodés (ce qui couvre `\u0073k-…`). Les chaînes et les noms sont contrôlés pendant la lecture (`KeyScan`), sans `serde_json::Value`, qui ne garderait que le dernier de deux champs de même nom. Sinon, une réponse 2xx devient un échec local (« Réponse de Mammouth inutilisable » ; clé trouvée : refus vide, voir plus bas), et un autre statut revient avec un corps vide, que le SDK affiche par son statut (« Clé refusée (401)… »). Un 2xx autre que 200, ou un statut au-delà de 599, est aussi un échec local : le SDK n'aurait rien à lire (l'adaptateur de la vue web refuse de même 204, 205 et 304). Elle ne rend que deux en-têtes : `content-type` (écrit par le Rust : `application/json` pour un corps non vide, rien pour un corps vide, jamais retiré pour une autre raison) et `request-id` (1 à 128 caractères `[A-Za-z0-9_-]`, jeté s'il contient la clé). Tout texte qui sort de `transport` après la lecture de la clé, succès comme erreur, est contrôlé une dernière fois (`outbound`, sur le texte exact que `seal` produit et que `tauri::ipc::Response` envoie tel quel) et refusé avec un texte vide s'il la contient ; la vue web écrit alors la phrase `LEAK_MESSAGE`. Hors de cette garantie : une clé écrite exprès sous une autre forme (base64, coupée, nombre dans une autre notation) ; une clé absurde (`json`, `a`) rend l'app inutilisable, sans fuite. La preuve réelle de ce transport se lance à la main, avec la demande d'accès de macOS : test ignoré `real_call_to_mammouth` (`cargo test --locked --manifest-path apps/desktop/src-tauri/Cargo.toml -- --ignored --exact --show-output ai_transport::tests::real_call_to_mammouth`, un seul appel payé).
- Créer l'identité de signature (une fois, par l'utilisateur) : installer Xcode (App Store) et l'ouvrir une fois. Puis Xcode → Settings… (⌘,) → Accounts → « + » → Apple Account, se connecter (la « Personal Team » gratuite suffit). Choisir l'équipe → Manage Certificates… → « + » → Apple Development. Le certificat et sa clé privée vont dans le trousseau de session. Le nom exact de l'identité est le texte entre guillemets que donne `security find-identity -v -p codesigning` (`"Apple Development: … (…)"` ; le code entre parenthèses n'est pas le Team ID). Si deux identités portent le même nom, passer à la place l'empreinte de 40 caractères de la ligne voulue (pas encore essayé avec la CLI Tauri). Si la commande rend `0 valid identities found` alors que la même commande sans `-v` en liste une, lire la raison qu'elle affiche. Au lot 5 bis, la cause était le certificat intermédiaire « Apple Worldwide Developer Relations Certification Authority » **G3**, absent du trousseau (seul l'ancien, expiré, était dans `System.keychain`). Pour l'ajouter : `curl -fsSLo /tmp/AppleWWDRCAG3.cer https://www.apple.com/certificateauthority/AppleWWDRCAG3.cer && open /tmp/AppleWWDRCAG3.cer`, puis choisir le trousseau de session, puis relancer `security find-identity -v -p codesigning` : l'identité doit y être valide. Aucun agent n'écrit dans le trousseau : cette étape et les suppressions d'entrées sont faites par l'utilisateur.
- Essayer l'app comme en production, depuis la racine : `env -u APPLE_CERTIFICATE -u APPLE_CERTIFICATE_PASSWORD -u APPLE_ID -u APPLE_PASSWORD -u APPLE_TEAM_ID -u APPLE_API_KEY -u APPLE_API_ISSUER -u APPLE_API_KEY_PATH APPLE_SIGNING_IDENTITY="Apple Development: … (…)" pnpm --filter desktop tauri build --debug --bundles app` donne `apps/desktop/src-tauri/target/debug/bundle/macos/Family Meals Helper.app`, signé, avec la CSP de production et l'inspecteur web (ouvert dans un `.app` signé au lot 5 bis, conforme). Les `env -u` empêchent la CLI Tauri d'importer un certificat dans un trousseau temporaire ou de tenter une notarisation. Au premier build, macOS peut demander que `codesign` utilise la clé privée de l'identité : mot de passe de session, puis « Toujours autoriser ». Ce clic autorise durablement `codesign` à utiliser cette clé ; sans lui, chaque build redemande. Pour vérifier la signature : `APP="apps/desktop/src-tauri/target/debug/bundle/macos/Family Meals Helper.app"; codesign --verify --strict --verbose=2 "$APP"; codesign -dv --verbose=4 "$APP"; codesign -d -r- "$APP"`. La première commande ne doit signaler aucune erreur ; elle passe aussi pour un build ad hoc, c'est la deuxième qui dit si le build est signé. La deuxième montre `Authority=Apple Development: …` et un `TeamIdentifier` de 10 caractères (`not set` : build ad hoc, la variable manquait). La troisième montre l'exigence désignée (DR), la règle qu'une autre version doit remplir pour être reconnue comme la même app. Le `CDHash` est l'empreinte du binaire signé : il change dès que le code change. Contre-épreuve du lot 5 bis (2026-11-16, macOS 26.7.3, certificat Apple Development d'une Personal Team) : A et B avaient des `CDHash` différents et la même exigence désignée. A a enregistré une clé ; B l'a lue deux fois sans demande d'accès, puis supprimée. Pour vérifier qu'un nouveau build remplit l'exigence du précédent : avant de reconstruire, garder celle de l'ancien avec `codesign -d -r- "$APP" 2>&1 | sed -n 's/^designated => //p' > /tmp/fmh-dr.txt`. Après le build, `test -s /tmp/fmh-dr.txt && codesign --verify --strict -R "=$(cat /tmp/fmh-dr.txt)" --verbose=2 "$APP"` doit rendre 0 (3 : exigence non remplie ; 1 : exigence non gardée ou échec de la vérification, voir le message de `codesign`), et `codesign -dv --verbose=4 "$APP" 2>&1 | grep CDHash` doit montrer un `CDHash` différent de l'ancien. Ne pas ouvrir l'app de dev et le `.app` ensemble : ils partagent la base, et la seconde instance voit ses réglages refusés.
- Trousseau et signature ad hoc : `tauri dev`, et un `tauri build` sans `APPLE_SIGNING_IDENTITY`, signent ad hoc (sans identité). Chaque recompilation qui change le binaire est alors une autre app pour le trousseau, qui redemande l'accès. Une version ad hoc et le `.app` signé sont aussi deux apps différentes pour le trousseau. D'après ce qu'on a constaté au lot 5 entre deux versions ad hoc, l'une devrait pouvoir remplacer la clé enregistrée par l'autre, après « Autoriser », mais pas la supprimer. Enregistrer donc la clé depuis le `.app` signé. Une entrée créée avant la signature, ou par une version ad hoc, se supprime une fois à la main : Trousseaux d'accès, chercher « com.familymealshelper.desktop », supprimer l'entrée, puis enregistrer la clé depuis le `.app` signé.
- Composer un menu (lots 1 à 3, sans détail ni PDF) : `pnpm --filter core compose "<demande>" [--exclude x] [--month 11] [--session-day dimanche] [--max-attempts 3] [--dry-run]`. `--session-day` (vendredi, samedi, dimanche ou lundi ; dimanche par défaut) fixe le jour de la session de cuisine, qui décide de la conservation. `compose` affiche aussi les constats `warning`, les plats « À congeler », la durée de session calculée, l'appareil d'appoint et le planning. `--dry-run` affiche les prompts sans réseau ni clé. Sans `--dry-run`, appel réel : clé dans `ANTHROPIC_API_KEY`, URL et modèle dans `ANTHROPIC_BASE_URL` / `ANTHROPIC_MODEL`. La clé de l'utilisateur est une clé Mammouth, lue depuis l'environnement : `ANTHROPIC_BASE_URL=https://api.mammouth.ai` et `ANTHROPIC_MODEL=claude-sonnet-5-5`, sans `FMH_DISABLE` (Mammouth accepte la sortie structurée, `effort` et le cache). `FMH_DISABLE=format,effort,cache` retire une fonction qu'un autre proxy refuserait. `pnpm --filter core smoke` fait un seul appel de test ; `pnpm --filter core season:import` régénère la table de saison (voir `docs/research/saison-fruits-legumes.md`).
- Produire la fiche (lot 4) : `pnpm --filter core batch "<demande>" [--out fiche.pdf] [--exclude x] [--month 11] [--session-day dimanche] [--max-attempts 3] [--dry-run]`. Elle enchaîne composition, détail et PDF. Sans `--out`, le PDF va dans `~/Downloads/menu-batch-AAAA-MM-JJ.pdf`, puis `-2`, `-3`… sans jamais écraser un fichier. `--out` doit finir par `.pdf`. Un `--out` relatif se comprend depuis le dossier où la commande est tapée, et un `--out` existant est remplacé. Codes de sortie : 0 fiche propre ; 1 fiche écrite avec un avertissement (plus de 3 h, ou repli sur les grandes phases) ; 2 pas de fiche (menu inutilisable, erreur d'usage ou locale). La clé, le dossier et les polices sont vérifiés avant tout appel payé. `--dry-run` affiche les prompts, sans réseau. La commande fait de 2 à 6 appels à l'IA : appels rares (clé Mammouth à 2 $/mois).
- Fiche d'exemple sans réseau ni clé : `pnpm --filter core pdf:fixture --out <fichier.pdf> [--fallback]` (`--fallback` : la fiche de repli).
- Depuis un sous-paquet, `pnpm -w lint` (ou `-w format:check`) lance le script racine.
- Ce projet est sur GitHub : https://github.com/bfigliuzzi/family-meals-helper. Le profil Codex du projet est `~/.codex/family-meals-helper.config.toml` (gpt-6.1-sol, effort high).

Les textes de l'interface, du PDF et des docs sont en français. Les identifiants de code sont en anglais.
